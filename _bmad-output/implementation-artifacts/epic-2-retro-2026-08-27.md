## Challenges Discovered

### 1. Story Sequencing Confusion (Process Signal)
**Observation:** Stories were marked "done" (Aug 13) but worked out-of-order due to dependencies between Stories 2-5 and 2-6.

**Timeline Evidence:**
- Stories 2-1 through 2-4: Linear, sequential completion (Aug 13)
- Stories 2-5 and 2-6: Tight coupling discovered during 2-6 implementation
- Story 2-6 required refinement until Aug 21 (8 days after marking "done")
- Story 2-7: Ran in parallel with 2-5/2-6 because it only consumed expense API (no domain coupling)

**Root Cause:** Acceptance criteria for Story 2-5 didn't explicitly require "split state serialization must be restorable for edit scenarios" — so Story 2-6's restore flow wasn't considered during 2-5 ACs.

**Actual Impact:** No schedule slips, but process was opaque. Team members worked in parallel without clear visibility into dependencies.

### 2. Definition of Done is Incomplete
**Discovery:** Story 2-5 was marked "done" (Aug 13) when its primary happy path worked, but the edit/restore scenario (which depends on split state serialization format) required refinement through Aug 21.

**What "Done" Meant (Incorrect):**
- ✅ Primary AC happy path implemented
- ✅ Unit tests pass
- ✗ Downstream scenarios not considered
- ✗ Data format not validated for future use

**Result:** Aug 13 status was misleading. Real completion was Aug 21.

### 3. Acceptance Criteria Incomplete for Cross-Story Dependencies
**Specific Example:** Story 2-5 ACs covered "user can save splits equally or unequally" but didn't explicitly require:
- Split method must be persisted in a restorable format
- Edit flow (Story 2-6) must be able to retrieve and reconstruct exact split configuration
- State management across multiple split method switches must initialize correctly

**Downstream Impact:** Story 2-6 implementation discovered gaps in 2-5's split state handling. Dana found edge cases during QA (state initialization timing issues) that required Charlie to refine code on Aug 21.

### 4. Epic 1 Action Items Not Applied in Epic 2
**Epic 1 Retro Action Item:** "Validate ACs at story creation: Verify display/feedback states are covered before marking ready-for-dev"

**Delivered Artifact:** `docs/review-checklist.md` created with security, API, UX, testing, and code quality sections

**What Happened in Epic 2:** Checklist existed but was not actively applied during story creation. Alice and Charlie didn't explicitly run through checklist for Stories 2-5/2-6 ACs.

**Lesson:** Creating a tool ≠ using it. Process must include explicit checkpoint.

### 5. Story 2-6 State Management Fragility
**QA Finding (Dana):** The edit flow's split method restoration logic works but has fragile state initialization behavior.

**Specific Issue:** Switching between split methods in the edit screen doesn't always initialize defaults correctly (timing-dependent behavior).

**Status:** Fixed as of Aug 21, but tight timing suggests potential for regression after deployment.

## Retrospective Insights

### 1. Tight Coupling Between Stories Must Surface During AC Creation
**Insight:** Story 2-5 and 2-6 weren't independent. Story 2-6's "restore split method" AC directly depends on Story 2-5's "persist split state" implementation.

**Root Cause:** Acceptance criteria reviews during story creation don't explicitly ask "what will downstream stories need from this story?"

**Impact:** Coupling discovered during implementation (2-6) rather than during planning. This caused refinement cycles that looked messy in timestamps.

**Prevention:** AC dependency coverage section in checklist (Action Item 1).

### 2. Parallel Work on Dependent Stories Works But is Risky
**Observation:** Elena started Story 2-7 (history display) while Charlie was still refining Stories 2-5 and 2-6 domain logic.

**Why it Worked:** 2-7 only consumed expense API (read-only), so it didn't depend on the refinement details.

**Risk:** Implicit pressure to "keep stories moving" can mask hidden dependencies. If 2-7 had required specific split state format, parallel work would have created blockers.

**Lesson:** Dependency matrix must exist before parallel work starts (Action Item 2).

### 3. Definition of Done Must Be Explicit and Stable
**Current State:** "Done" = feature works for primary scenario. But that's ambiguous for cross-story dependencies.

**What Happened:** Story 2-5 marked done when "split calculation works" (Aug 13), but not when "split state format is finalized for restoration use" (Aug 21).

**Result:** Sprint-status showed "done" but work was still ongoing. Eight-day gap between status and actual completion.

**Fix:** Formalized DoD must include "downstream dependencies validated" (Action Item 4).

### 4. Action Item Follow-Through Matters
**Epic 1 Delivered:** AC validation checklist in `docs/review-checklist.md`

**Epic 2 Reality:** Checklist existed but wasn't systematically applied

**Lesson:** Artifacts alone don't change behavior. Process checkpoints must be built in (e.g., "Charlie reviews all ACs against checklist before story goes to ready-for-dev").

### 5. QA Discovered Late-Stage Issues That Could Have Been Prevented
**Dana's Findings:**
- Story 2-5: Complex split logic required thorough edge-case testing (state transitions, multi-participant scenarios)
- Story 2-6: State initialization timing issues emerged during QA, requiring code refinement Aug 21

**Analysis:** These issues existed because ACs didn't cover cross-story scenarios. If Story 2-5 ACs had required "split state is restorable exactly as created," testing would have caught these issues earlier.

## Action Items

### Process Improvements (Prevent Future Coupling Issues)

#### Action Item 1: Create AC Template with Dependency Coverage
- **Description:** Extend `docs/review-checklist.md` with "AC Dependency Coverage" section
- **Guidance:** For each AC, explicitly ask:
  - Does this cover primary happy path? (Standard)
  - Does this cover error cases? (Standard)
  - Does this cover downstream stories' needs? (NEW)
  - If data is created (DB, API, state), is retrieval/restoration explicitly covered? (NEW)
- **Example:** Story 2-5 ACs should require "split method and participant amounts must be persisted in a format restorable by Story 2-6 edit flow"
- **Owner:** Alice (Product Owner) + Charlie (Senior Dev validation)
- **Deadline:** Aug 29, 2026
- **Success Criteria:** All Epic 3 stories use updated AC template; no split/balance coupling surprises
